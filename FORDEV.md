# МАИ.Команда: как устроен проект

Этот файл — точка входа для разработчика. Сервис помогает студентам найти проект, откликнуться на роль, собрать команду и получить контакты для связи с командой.

## 1. Как посмотреть результат на этом компьютере

В папке проекта подготовлено локальное окружение. Ничего не установлено как служба Windows.

1. Открой `START.cmd` двойным щелчком и дождись сообщения `Ready`.
2. Открой **http://127.0.0.1:3000**.
3. Когда закончишь, запусти `STOP.cmd`. База и созданные записи сохранятся.

Тестовые аккаунты, только для локальной демонстрации:

| Email | Роль |
| --- | --- |
| `author@example.com` | Автор демонстрационных проектов |
| `student@example.com` | Участник, может отправлять отклики |
| `moderator@example.com` | Модератор |
| `member@example.com` | Участник одной из команд |

Общий демонстрационный пароль: `DemoTeam2026!`. Эти данные из демо-набора, это не реальные студенты. На публичном сервере демо-аккаунтов быть не должно.

Для просмотра нескольких ролей удобно входить и выходить по очереди. Сессия хранится отдельно для каждой вкладки и переживает обновление страницы. Действующие сессии ограничены по времени.

Подготовленный запуск использует `.venv`, `frontend/node_modules` и `.local`: PostgreSQL 17, локальную базу `mai_dev`, логи, настройки путей к Node.js и случайный пароль локальной БД. Всё это исключено из Git. PostgreSQL слушает только `127.0.0.1:55432`, API — `127.0.0.1:8000`, интерфейс — `127.0.0.1:3000`.

`START.cmd` ничего не скачивает, не меняет системные настройки и не останавливает процессы, занявшие нужный порт. Если окружение не найдено, смотри обычную установку ниже. После переноса папки или удаления Codex путь к подготовленному Node.js может потребовать обновления в `.local/runtime.json`.

## 2. Стек простыми словами

| Часть | Технология | За что отвечает |
| --- | --- | --- |
| Интерфейс | React и обычный JavaScript | Страницы, формы, кнопки, отображение данных |
| Адреса страниц | React Router | Переходы `/projects/123`, `/dashboard` и другие |
| Сборка интерфейса | Vite | Запуск разработки и подготовка файлов для сервера |
| Оформление | Обычный CSS | Цвета, отступы, сетки и адаптация под телефон |
| Сервер | Python + FastAPI | Правила работы, проверка прав, API |
| Работа с базой | SQLAlchemy | Python-код для запросов к PostgreSQL |
| База | PostgreSQL | Пользователи, проекты, отклики, сессии, жалобы |
| Проверки | pytest | Автоматическая проверка логики сервера |

SQLAlchemy — **не отдельная база**. Он отправляет SQL-запросы в PostgreSQL. React — единственный UI-фреймворк; Next.js, Tailwind и TypeScript в текущей версии не используются. Prettier только форматирует исходный код.

## 3. Как части общаются

```text
Пользователь нажимает кнопку в React
    ↓
src/api.js отправляет HTTP-запрос /api/...
    ↓
Vite (разработка) или nginx (контейнер) передаёт его FastAPI
    ↓
FastAPI проверяет данные, вход и права
    ↓
SQLAlchemy читает/изменяет PostgreSQL
    ↓
Сервер возвращает JSON, React обновляет экран
```

Например, «Принять» отправляет `POST /applications/42/decision` с `{"status":"accepted"}`. Сервер проверяет, что запрос отправил автор проекта, набор открыт и место ещё свободно. Только затем меняет отклик и подтверждает действие интерфейсу.

Кнопки в браузере — удобство. Защита всегда на сервере: скрытая кнопка сама по себе не запрещает HTTP-запрос.

## 4. Карта папок

```text
backend/
  app/
    main.py             создание FastAPI, обработка ошибок, подключение маршрутов
    db.py               подключение к PostgreSQL, сессия работы с базой
    models.py           описание таблиц SQLAlchemy
    schemas.py          входные/выходные поля API и их проверка
    security.py         пароли, токены сессий, текущий пользователь, модератор
    services.py         общие проверки и формирование ответов
    routers/
      auth.py           регистрация, вход, выход, профили
      projects.py       каталог, проекты, редактирование, набор, мои команды
      applications.py   отклики, решения автора, отзыв, выход и удаление участника
      moderation.py     очередь публикаций и решения по ним
      reports.py        жалобы, ограничения, уведомления, история
    migrate.py          применение SQL-миграций по порядку
    seed.py             явная загрузка демонстрационных данных
  tests/                проверки API, прав, конкуренции и миграций
frontend/
  src/
    main.jsx            общий каркас, меню, маршруты, правила сообщества
    api.js              HTTP-запросы, обработка ошибок, общие подписи
    auth.jsx            состояние входа и защита страниц
    hooks.js            загрузка данных и обработка действий
    styles.css          весь внешний вид, включая мобильные правила
    components/ui.jsx   карточка проекта, статусы, ошибки, форма жалобы
    pages/              отдельные экраны
  vite.config.js        настройка сборки и прокси /api
  nginx.conf            раздача готовой сборки в контейнере
database/
  migrations/           последовательные SQL-изменения структуры
  seeds/                только вымышленные демонстрационные данные
scripts/                локальный запуск и упаковка исходников
compose.yaml            совместный запуск PostgreSQL, API и интерфейса
```

## 5. Что находится на фронтенде

| Файл экрана | Адрес | Что делает |
| --- | --- | --- |
| `Catalog.jsx` | `/` | Поиск, направление, формат, навык, свободные места, страницы каталога |
| `Project.jsx` | `/projects/:id` | Описание, роли, состав, отклик, контакт и входящие заявки автора |
| `Editor.jsx` | `/projects/new`, `/projects/:id/edit` | Создание/редактирование проекта и ролей |
| `Dashboard.jsx` | `/dashboard` | Команды, свои проекты, отклики, жалобы и уведомления |
| `Account.jsx` | `/login`, `/register`, `/profile`, `/people/:id` | Вход и профили |
| `Moderation.jsx` | `/moderation` | Проверка публикаций, жалобы, блокировки и история |

Фильтры и номер страницы каталога находятся в URL. Ссылку можно скопировать, обновление страницы не сбрасывает выбранные фильтры. Вкладки кабинета используют `?tab=...`.

`useResource` отвечает за загрузку, ошибку, повторную попытку и отмену устаревшего запроса. `useAction` отключает повторный запуск действия, пока выполняется первый запрос. React выводит пользовательский текст как текст; HTML из описаний не исполняется.

## 6. Основные таблицы и связи

| Таблица | Смысл |
| --- | --- |
| `users` | Профиль, хеш пароля, роль, состояние блокировки |
| `sessions` | Хеш токена входа, пользователь, время окончания |
| `projects` | Автор, описание, направление, публикация, набор, приватный контакт |
| `vacancies` | Роли внутри проекта и количество мест |
| `applications` | Отклик пользователя на конкретную роль и его состояние |
| `reports` | Жалоба на проект **или** профиль, причина и результат рассмотрения |
| `moderation_events` | Кто, когда, какое решение принял и почему |
| `schema_migrations` | Какие миграции уже применены и их контрольные суммы |

У проекта один автор и несколько ролей. Отклик связан с пользователем и ролью. **Команда — автор плюс принятые отклики.** Отдельная дублирующая таблица участников не нужна.

## 7. Логика проекта, откликов и команды

Публикация и набор — независимые поля:

| Поле | Значения |
| --- | --- |
| `status` | `pending` — проверка; `published` — опубликован; `rejected` — нужны исправления; `hidden` — скрыт модератором |
| `recruitment_open` | `true` — автор открыл набор; `false` — автор закрыл набор |

Отклик разрешён, только если проект опубликован, набор открыт, автор не заблокирован и есть место. Закрытие набора оставляет опубликованный проект в каталоге, но фильтр «Есть свободные места» его исключает.

Новый проект отправляется на проверку. Редактирование также переводит его в `pending`. Автор, модератор и принятые участники сохраняют доступ, остальные временно не видят страницу. У скрытого проекта изменения запрещены до повторного решения модератора: нельзя обойти скрытие простым редактированием.

Состояния отклика:

```text
pending → accepted / rejected / withdrawn
accepted → left / removed
withdrawn или left → новый pending на той же роли
```

Повторный отклик на отклонённую роль или после удаления автором запрещён. После самостоятельного отзыва/выхода можно откликнуться снова. Если человека приняли на одну роль, остальные ожидающие отклики этого человека в том же проекте отклоняются.

При принятии, отзыве и изменении состава сервер блокирует строку проекта на время транзакции (`SELECT … FOR UPDATE`). Поэтому два параллельных решения не занимают одно последнее место. Вместимость роли нельзя уменьшить ниже числа принятых участников; роль с откликами нельзя удалить.

## 8. Контакты, вход и права

- Посетитель видит каталог и опубликованные проекты.
- Вошедший студент может заполнить профиль, создать проект, откликнуться и пожаловаться.
- Автор управляет своим проектом и входящими заявками.
- Модератор проверяет публикации и жалобы. Он не может одобрить свой проект или рассмотреть свою жалобу/жалобу на себя.
- Роль модератора нельзя получить через регистрацию или изменение профиля. Для реального запуска её назначает администратор базы доверенным аккаунтам.
- Email есть только в собственном ответе `/me`. Пароли и хеши токенов не возвращаются клиенту.
- Контакт `team_contact` принимает текст до 500 символов, включая ссылки, email и телефоны. Он доступен автору, модератору и принятым участникам. В каталоге и для постороннего посетителя это пустая строка.
- Комментарий к публикации видят только автор и модераторы.
- Пароль хешируется scrypt с индивидуальной солью. В браузер выдаётся случайный токен, в базе хранится его хеш. Выход удаляет серверную сессию.
- Блокировка отзывает сессии, запрещает вход и скрывает проекты автора из публичного просмотра. Разблокировка не возвращает старые токены: нужно войти заново.

## 9. Жалобы и модерация

Кнопка жалобы есть на проекте и в профиле. Причины: спам, оскорбления, обман, другое. Пользователь видит свои обращения в кабинете. Чужие жалобы и личность заявителя автору не выдаются.

На одну цель разрешена одна ожидающая жалоба от пользователя; максимум 10 ожидающих жалоб. Сам факт жалобы ничего не скрывает. Модератор выбирает:

1. Нарушения нет — закрывает обращение.
2. Замечание — адресат видит объяснение в уведомлениях.
3. Скрыть проект — убирает его из публичного каталога; он попадает в очередь повторного рассмотрения.
4. Заблокировать аккаунт — применяется к автору проекта или пользователю из жалобы.

Каждое решение записывается в историю с модератором, временем и причиной. Модераторы не могут блокировать себя или других модераторов. Разблокировка доступна в отдельной вкладке. В объяснениях нельзя писать имя заявителя — текст решения видят участники рассмотрения.

## 10. Обычный запуск на другом компьютере

### Вариант A: Docker Compose

Нужен установленный Docker с Compose и запущенный движок Linux containers в Docker Desktop. Если запущена версия через `START.cmd`, останови её через `STOP.cmd`, чтобы освободить порты 3000 и 8000. Из корня проекта:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
# Перед первым запуском задай свой POSTGRES_PASSWORD в .env (буквы и цифры).
docker compose up --build -d --wait
```

Сначала запускается PostgreSQL, затем миграции, API и интерфейс. Сайт: `http://localhost:3000`, описание API: `http://localhost:8000/docs`.

Демо-данные добавляются только явно: в `.env` установи `ALLOW_DEMO_SEED=true`, затем:

```powershell
docker compose --profile demo run --rm seed
```

Проект Compose называется `mai-team` независимо от имени папки. PostgreSQL хранит данные в томе `mai-team_pgdata`. Это отдельная база: данные подготовленной Windows-версии автоматически не переносятся. Интерфейс собирается Vite и обслуживается nginx, который также передаёт `/api/` в FastAPI. Python и Node на компьютере для этого запуска не нужны.

Остановка с сохранением базы: `docker compose down`. Не добавляй `-v`, если нужны данные: этот флаг удаляет том базы. Состояние контейнеров: `docker compose ps -a`. Логи: `docker compose logs --tail 100`. После изменения кода повтори команду запуска с `--build`.

Конфигурация проверена командой `docker compose --env-file .env.example config --quiet`. Контейнерная сборка пока не проверена: Docker Desktop установлен, но движок не отвечает (`dockerDesktopLinuxEngine` отсутствует). API и миграции ранее проверены на отдельном настоящем PostgreSQL.

### Вариант B: Python + Node.js + PostgreSQL

Нужны Python 3.12+, Node.js 22.12+ (проверено на 24), pnpm и доступная PostgreSQL 17. Создай отдельную базу `mai` и пользователя. Затем из корня:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
$env:DATABASE_URL = 'postgresql+psycopg://USER:PASSWORD@127.0.0.1:5432/mai'
cd backend
..\.venv\Scripts\python.exe -m app.migrate
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Во втором терминале из `frontend`:

```powershell
pnpm install --frozen-lockfile
pnpm dev
```

В Windows можно использовать `pnpm.cmd`, если запуск PowerShell-скрипта `pnpm.ps1` запрещён. Менять системную ExecutionPolicy не нужно. Vite проксирует `/api` на `127.0.0.1:8000`; адрес можно изменить переменной `API_PROXY_TARGET`. Настоящий пароль БД не коммить. Для специальных символов в пароле используй URL-кодирование.

Сборка фронтенда: `pnpm build`. Результат — `frontend/dist`. `pnpm preview` показывает собранные файлы, но для работы API нужен прокси; обычный локальный запуск — `pnpm dev`, контейнерный — nginx из Compose.

## 11. Миграции и существующие данные

Схема меняется SQL-файлами `001_...sql`, `002_...sql` и далее. `python -m app.migrate` выполняет только новые файлы. Запись о миграции и её изменения фиксируются одной транзакцией; повторный запуск безопасен. Уже применённые миграции не редактируем: контрольная сумма специально обнаружит изменение.

Миграция `002` добавляет набор, контакт, блокировки, жалобы и историю, не удаляя пользователей, проекты или отклики. Старый статус `closed` переводится в `pending` с закрытым набором: старая схема не сохраняла, был ли проект одобрен до закрытия. Такие проекты нужно повторно проверить. Участники сохраняются.

Перед применением к настоящей базе сделай резервную копию. Переключение Git-ветки **не откатывает базу**. Для возврата старой версии используй отдельную БД либо заранее сделанную резервную копию.

## 12. Тесты и изменение кода

Быстрые тесты на SQLite (только тестовая подмена, рабочая база — PostgreSQL):

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
```

Полная проверка PostgreSQL через Compose:

```powershell
docker compose --profile test run --rm test
```

Или укажи `TEST_DATABASE_URL` на **отдельную одноразовую базу с окончанием `_test`** и `ALLOW_TEST_DB_RESET=true`. Тесты очищают её схему. Не подставляй рабочую базу.

Проверяются права, приватность контактов, модерация, переполнение роли, отзыв и выход, блокировки, жалобы, пагинация, параллельные решения и обновление старой схемы. Точный результат текущей проверки — в `docs/verification.md`.

Когда добавляешь поле: SQL-миграция → `models.py` → `schemas.py` → маршрут/ответ → форма React → проверка сценария. Когда меняешь внешний вид: обычно достаточно `styles.css` и конкретного компонента. Когда добавляешь страницу: файл в `pages` и маршрут в `main.jsx`.

Форматирование фронтенда: `pnpm format`. OpenAPI доступен в `/docs`, копия контракта — `docs/openapi.json`.

## 13. Что сознательно оставлено на следующий этап

- Каталог людей и приглашения, внутренний чат, рекомендации и рейтинги.
- Восстановление пароля, подтверждение email и проверка принадлежности к МАИ: сейчас зарегистрироваться можно с любым валидным адресом.
- Черновики и отдельная опубликованная версия: правки пока временно снимают проект с каталога.
- Уведомления по email/Telegram: сейчас они только внутри кабинета, без фоновых рассылок.
- Массовая нагрузка: ограничитель входа работает в памяти одного процесса; для нескольких процессов нужен общий ограничитель. Большие личные списки и очереди модерации позже стоит разбить на страницы.
- HTTPS, резервное копирование по расписанию, домен и реальное развёртывание — отдельная задача. Ничего не опубликовано.

## 14. Локальная история и исходники

Изменения находятся в ветке `feature/service-rework`, исходная `main` сохранена. Коммиты сделаны только локально, push не выполнялся. Смотри `git log --oneline`, `git status`, `git diff main...feature/service-rework`.

`.local` содержит окружение и данные для проверки, а не исходный код. Не отправляй эту папку в Git или архив для команды: внутри пароль локальной БД и база. `scripts/package_sources.py` собирает архив исходников внутри `.local` и исключает окружение, секреты и зависимости.
